# Analysis: R-20260726-0108

## Overview

- **Request ID:** R-20260726-0108
- **Request title:** Партньори Adreo image and timeline arrow buttons

### Background

The partners section currently presents three partner entities — Инженерни Системи, Корект Проект, and Адрео — but only the first two render as logo images. Адрео is shown as a styled text wordmark (`<span class="at-partner__wordmark">Адрео</span>`) because no partner image was available at the time of the original implementation. The partner image file `wp-content/uploads/2026/07/adreo.png` is now present in the workspace and the developer wants it rendered consistently with the other partners.

Additionally, the desktop timeline navigation currently provides Previous and Next controls as a labelled button row placed below the timeline rail (`.at-tl-controls` div). The developer wants these navigation affordances relocated so they appear as arrow-image controls integrated into the ends of the timeline rail itself, providing more intuitive in-line navigation without a separate button strip below.

### Scope

- Аdreo partner list item in the partners section of all applicable BG and EN homepage documents: replacing the text wordmark span with an `<img>` element pointing to `wp-content/uploads/2026/07/adreo.png`.
- Desktop timeline previous/next navigation buttons in all timeline-bearing homepage documents: repositioning the buttons from the `.at-tl-controls` div below the timeline to the ends of the timeline rail as visually integrated arrow-image controls.
- CSS changes in the shared stylesheet (`wp-content/themes/atistat/assets/css/main.css`) and/or document-local style blocks to support the new arrow layout.
- `context.md` update to reflect the partners section now using a logo image for Адрео and to document the arrow-integrated timeline navigation model.

### Out of scope

- Mobile stacked-card timeline layout (`.at-tlcard` elements) — mobile navigation is unchanged.
- Project detail pages under `proekti/`.
- `opit/index.html` partners section (absent from that document).
- Server configuration, CMS, or WordPress changes.
- Content or structure of the six project JSON records in `wp-json/`.
- Any gallery dialog, FAQ, hero section, or contact block changes.

**Industry knowledge**

- *Overlay navigation pattern — Nielsen Norman Group:* Carousel and timeline controls embedded at the edges of the scroll track (chevron buttons overlaid on the scrollable area) are recommended over external button strips when horizontal space is at a premium. Key trade-off: the overlay must not obscure content near the edges; this is typically resolved by reserving a padding zone inside the scroll container or clipping content behind the overlay with a gradient fade. Applicability: directly relevant; the current `.at-tl-edge` gradient already fulfils the fade role, so extending it to include a clickable arrow on top is architecturally sound.

- *WCAG 2.1 — Success Criterion 2.5.5 (Target Size):* Interactive controls should meet a minimum 44×44 CSS-pixel touch target. The current `.at-tl-control` rule already specifies `min-width: 44px; min-height: 44px`. Repositioned arrow buttons must preserve this constraint to avoid accessibility regression. Applicability: high; the repositioned controls must not shrink below 44×44px regardless of their new position.

- *SVG icon conventions — Material Design and ARIA:* When an icon-only button conveys its entire meaning through a visible image (SVG or raster), the `aria-label` on the `<button>` element is the correct and sufficient text alternative; no additional visible text label is required. The icon-only pattern is standard for navigation arrows that pair with adjacent visible context (the timeline itself). Applicability: supports removing the visible text labels ("Предишен"/"Следващ") from the buttons if they are repositioned as icon-only arrow controls, provided `aria-label` values are retained.

### Edge Cases

- If `adreo.png` fails to load in a user's browser (network error or path mismatch), no fallback text is displayed for the partner; the anchor's `aria-label` remains the only textual identification. The alt text must be non-empty to provide a fallback.
- If the arrow buttons are placed inside the scrollable `.at-tl-buildings` container, they will scroll out of view when the user pans the rail, losing the persistent navigation affordance. Buttons must be placed outside the scroll container or positioned as non-scrolling overlays.
- The `at-tl-rail-shell` uses `position` context (implied by child absolute elements); arrow buttons added inside it and styled with `position: absolute` at the edges will remain fixed relative to the shell even as the inner rail scrolls — this is the correct placement if overlay is chosen.
- At the first and last milestone, the current disabled buttons use `opacity: 0.38`. If the arrows are styled differently (e.g., hidden when disabled), keyboard-only users relying on the `:disabled` state for boundary feedback would lose that affordance unless an alternative indicator is provided.
- The `opit/index.html` timeline currently uses identical HTML markup to the five root homepages. If the arrow change is applied to root homepages only, `opit/index.html` will diverge and the shared-asset tests may flag parity failures.
- The reduced-motion media query already covers `.at-tl-control` transitions; new arrow elements using the same class inherit this coverage automatically. New classes introduced for the arrows must be added to the reduced-motion block manually.
- The CSS duplicate (`wp-content/themes/atistat/assets/css/main.css` plus an identical copy) must be updated in both locations; editing only one will create a byte-inequivalence flagged by tests.

## Decision Register

### Decision Points

#### Decision Point: Adreo image scope (DP-001)

- **Tag:** ask
- **Rationale:** The developer's input states "For BG and EN pages" but does not specify whether `index.html` (the primary Bulgarian canonical homepage) is included. `index.html` serves the same content as `index-bg.html` and is the site root; treating it as a "BG page" is plausible, but the developer may intend only the four explicit locale variants (`index-bg.html`, `index-en.html`, `index.html?lang=bg.html`, `index.html?lang=en.html`).

- **Alternative A:** Apply to all five BG/EN documents including `index.html` (primary Bulgarian).
  - Benefits: Maintains parity across the primary homepage and its locale variants; prevents divergence.
  - Drawbacks: Developer may not have intended to touch the primary `index.html` separately.
  - Impact: Five files modified.

- **Alternative B:** Apply only to the four explicit BG/EN variant files, excluding `index.html`.
  - Benefits: Matches the literal phrase "BG and EN pages" if `index.html` is considered the default/root page rather than a BG-specific page.
  - Drawbacks: Leaves `index.html` with a wordmark while other pages show a logo; creates inconsistency.
  - Impact: Four files modified; `index.html` retains wordmark.

#### Decision Point: Adreo alt text (DP-002)

- **Tag:** ask
- **Rationale:** The other two partner images use Bulgarian brand names as alt text (`alt="Инженерни Системи"`, `alt="Корект Проект"`). The Adreo brand uses a Latin-script name on its website (`adreo.bg`). The correct alt text language is not specified in the input.

- **Alternative A:** Use Bulgarian Cyrillic — `alt="Адрео"`.
  - Benefits: Consistent with the existing partner alt-text convention.
  - Drawbacks: The brand's own name uses Latin script; Cyrillic may misrepresent the brand.
  - Impact: Same alt text in all five documents.

- **Alternative B:** Use Latin script — `alt="Adreo"`.
  - Benefits: Matches the brand's self-identification on `adreo.bg`.
  - Drawbacks: Breaks the all-Bulgarian alt-text convention used by the other two partners.
  - Impact: Same alt text in all five documents.

- **Alternative C:** Use language-appropriate alt text — `alt="Адрео"` in BG files, `alt="Adreo"` in EN files.
  - Benefits: Aligns with the existing language-differentiated `aria-label` pattern on the Adreo link element.
  - Drawbacks: Adds a small inconsistency: EN files would have one alt text while BG files have another.
  - Impact: Alt text differs between BG and EN document variants.

#### Decision Point: Arrow DOM position (DP-003)

- **Tag:** ask
- **Rationale:** The "ends of the timeline itself" phrase identifies the visual target but not the DOM location. Several structurally valid positions exist, each with different CSS and JS implications.

- **Alternative A:** Place arrow buttons inside `at-tl-rail-shell`, alongside the existing edge fade spans, as absolutely-positioned overlays at the left and right edges.
  - Benefits: Visually aligned with the gradient edge fades; can use a z-index above 7 to receive clicks above the fades; the `at-tl-rail-shell` already provides a positioned container.
  - Drawbacks: Requires explicit `pointer-events: auto` override since the shell context has edge spans with `pointer-events: none`; care needed to ensure buttons don't interfere with the scrollable rail.
  - Impact: Minimal HTML restructure; CSS adds `position: absolute; pointer-events: auto` on buttons.

- **Alternative B:** Place arrow buttons inside `at-tl-stage`, as absolutely-positioned overlays on the outer container, outside `at-tl-rail-shell`.
  - Benefits: Cleaner separation between the scroll-indicator fades (inside shell) and navigation controls (outside shell); no pointer-events conflict.
  - Drawbacks: Requires `position: relative` confirmation on `at-tl-stage`; visual alignment with the rail edges requires careful CSS.
  - Impact: Moderate HTML restructure; buttons move to a sibling position of `at-tl-rail-shell`.

- **Alternative C:** Place arrow buttons inside `at-tl-desktop` as siblings of `at-tl-stage`, absolutely positioned to overlap the stage ends.
  - Benefits: Maximum layout flexibility; easiest to control overlap with year labels at the start/end.
  - Drawbacks: Requires `position: relative` on `at-tl-desktop`; most complex to align precisely with rail visual edges.
  - Impact: Largest HTML restructure among the three options.

#### Decision Point: Arrow visual format (DP-004)

- **Tag:** ask
- **Rationale:** The developer requests "arrow images" without specifying a format. Multiple technically valid formats exist with different accessibility, maintainability, and file-count implications.

- **Alternative A:** SVG inline in HTML — embed a small SVG path directly inside the button element.
  - Benefits: Scalable at any size; styleable via CSS fill/stroke; no extra HTTP request; consistent rendering across browsers.
  - Drawbacks: Adds SVG markup inside each HTML file; must be duplicated across all six timeline documents.
  - Impact: Moderate HTML change per document.

- **Alternative B:** CSS-drawn arrows using `border` or `clip-path` pseudo-elements — no image files needed.
  - Benefits: Zero extra files; fully scalable; easily themed with CSS variables.
  - Drawbacks: CSS shapes are less visually expressive than SVG; clip-path may need prefixes on older browsers.
  - Impact: CSS-only change; no HTML image content.

- **Alternative C:** External image file (.svg or .png) referenced via `<img>` or CSS `background-image`.
  - Benefits: Simplest HTML; image can be shared and cached; easiest to swap visually.
  - Drawbacks: Requires an additional asset file to be created and stored in the images directory; one extra HTTP request per page load.
  - Impact: New image asset + CSS reference change.

- **Alternative D:** Unicode/text characters (current `←`/`→`) repositioned and styled with CSS.
  - Benefits: Zero new assets; minimal change from current implementation.
  - Drawbacks: Does not meet the "arrow images" intent; still text-based even if visually repositioned.
  - Impact: CSS-only repositioning; no structural or asset change.

#### Decision Point: Arrow visual style (DP-005)

- **Tag:** ask
- **Rationale:** The developer has not specified the visual design of the arrow icons. The choice determines the visual language of the navigation controls.

- **Alternative A:** Simple chevron (‹ ›) — thin, minimal directional indicator.
  - Benefits: Lightweight, recognizable, consistent with most modern timeline/carousel patterns.
  - Drawbacks: May be small and low-visibility at rail edges.
  - Impact: One SVG path or CSS shape per direction.

- **Alternative B:** Filled directional triangle (▶ / ◀) — solid filled arrow.
  - Benefits: High contrast and visibility at rail edges; immediately recognizable.
  - Drawbacks: Can feel heavy if oversized.
  - Impact: One SVG path or CSS shape per direction.

- **Alternative C:** Circular button with arrow icon inside — icon inside a solid or outlined circle.
  - Benefits: Clear interactive affordance; provides a definite 44×44px hit area visually; consistent with Material Design / iOS navigation patterns.
  - Drawbacks: Larger visual footprint that may overlap more timeline content.
  - Impact: More complex CSS/SVG; adds a circle background to the button.

#### Decision Point: Arrow text labels (DP-006)

- **Tag:** ask
- **Rationale:** The current buttons display both visible text ("Предишен"/"Следващ") and an aria-label. Once relocated to within the rail ends, the visible text may not fit or may be visually undesirable in an icon-only arrow presentation.

- **Alternative A:** Remove visible text labels; keep only the arrow image and `aria-label` attribute.
  - Benefits: Clean icon-only appearance appropriate for an in-rail arrow; `aria-label` preserves screen-reader accessibility.
  - Drawbacks: No visible text hint for keyboard-only users who may not associate the arrow icon with "previous/next tab" semantics.
  - Impact: HTML and CSS simplification; must verify `aria-label` is retained.

- **Alternative B:** Retain visible text labels alongside the arrow image.
  - Benefits: Maximum clarity for all users including those unfamiliar with the arrow convention.
  - Drawbacks: Labels may be too wide to fit inside a rail-end overlay; may overlap milestone buttons.
  - Impact: Minimal HTML change; layout must accommodate label width.

- **Alternative C:** Move text labels to a visually hidden (but screen-reader-visible) `<span class="sr-only">` alongside the arrow image.
  - Benefits: Screen readers still announce the label text; no visible text clutters the arrow overlay.
  - Drawbacks: Adds a hidden span to each button; requires a `.sr-only` CSS utility class if not already present.
  - Impact: Small HTML addition; CSS utility class needed.

#### Decision Point: Edge fades fate (DP-007)

- **Tag:** ask
- **Rationale:** The existing `at-tl-edge` spans provide a gradient fade visual at rail edges and are required by the JS. With arrow buttons occupying the same edge area, the visual relationship between the fades and arrows must be defined.

- **Alternative A:** Keep edge fades unchanged; position arrow buttons on top of the fades (z-index above 7).
  - Benefits: JS requirement satisfied trivially; gradient fades remain as a "more content" indicator behind the arrows.
  - Drawbacks: Two overlapping elements at each end (fade + button); potential visual complexity.
  - Impact: No change to edge span markup or CSS; only button positioning added.

- **Alternative B:** Remove the gradient background from edge spans when arrows are visible; arrows alone signal the rail boundary state.
  - Benefits: Cleaner visual; arrow buttons take over the "there is more content here" communication role.
  - Drawbacks: Edge spans must remain in the DOM (JS requirement); their CSS must be overridden to suppress the gradient.
  - Impact: CSS change to `.at-tl-edge` gradient rule; spans remain in HTML.

- **Alternative C:** Integrate the gradient into the arrow button's CSS background, removing it from the separate edge spans.
  - Benefits: Single element handles both gradient and interactivity at each end.
  - Drawbacks: Edge spans must still remain in the DOM (JS requirement); combining gradient with button background limits design flexibility.

#### Decision Point: Arrow scroll-area constraint (DP-013)

- **Tag:** ask
- **Rationale:** The `.at-tl-buildings` element (the scrollable rail) is the innermost scroll container. If arrow buttons are positioned inside or relative to a parent that itself scrolls, the buttons may disappear when the user pans the rail. The positioning model must guarantee the arrows remain stationary as the rail scrolls.

- **Alternative A:** Position arrows as absolute overlays on `at-tl-rail-shell` (non-scrolling container).
  - Benefits: `at-tl-rail-shell` does not scroll; its children with `position: absolute` remain fixed within the shell as the inner `at-tl-buildings` rail scrolls.
  - Drawbacks: Requires the shell to be a positioned element (confirm or add `position: relative`).
  - Impact: CSS `position: absolute` on buttons within the shell; shell gets `position: relative` if not already.

- **Alternative B:** Position arrows as absolute overlays on `at-tl-stage` (outer container).
  - Benefits: Even further from the scroll container; clear layout hierarchy.
  - Drawbacks: Stage width includes the year-label columns; arrow alignment with rail edges needs offset calculation.
  - Impact: CSS with explicit left/right offsets accounting for year-label widths.

- **Alternative C:** Position arrows using CSS `position: sticky` inside `at-tl-rail-shell`.
  - Benefits: Sticky positioning naturally keeps elements at the edges as the user scrolls.
  - Drawbacks: `position: sticky` inside an overflow scroll parent has limited browser-support guarantees in nested scroll contexts; behavior may be unpredictable.
  - Impact: CSS `position: sticky` experiment; no HTML change needed.
