## Overview

- Request ID: R-20260726-0836
- Request title: Prioritize evidence cards and optimize gallery mosaics

### Background

The Experience section currently places a visually dominant desktop timeline before the selected evidence card, hides chronological navigation at widths of 860px or less, and renders tiny mosaic previews from full-resolution gallery files without a persistent visual cue that the mosaics open a gallery. The developer wants the evidence cards to lead the hierarchy, chronological navigation to remain available on all supported layouts, and normal-page gallery previews to become both lightweight and obviously interactive.

### Scope

The change covers the Experience markup in `index.html`, `index-bg.html`, `index-en.html`, `index.html?lang=bg.html`, `index.html?lang=en.html`, and `opit/index.html`; both copies of the shared CSS and JavaScript; 28 new local 160×160 WebP mosaic thumbnails; static regression tests and the browser interaction fixture; and the corresponding current-state and residual-risk entries in `.aib_memory/context.md`. It includes desktop hierarchy and scale changes, a 13-marker responsive navigation rail, localized gallery affordances, thumbnail substitution only in mosaic launchers, cross-route and shared-asset parity, reduced-motion handling, keyboard and focus behavior, and 320px overflow protection.

### Out of scope

The request excludes optimization or replacement of full-resolution images inside the opened gallery dialog, removal of original PNG/JPEG gallery assets, evidence-card redesign or enlargement, removal or filtering of responsive stacked cards, project-detail content changes, changes to gallery-dialog behavior beyond preserving it, and changes to the 13 milestones or their chronology.

### Industry Knowledge

- The WAI-ARIA Authoring Practices [Tabs Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) supports the existing desktop automatic-activation behavior because all panels are already present and can display without network latency. It also states that horizontal tablists should leave Up/Down Arrow behavior to normal page scrolling. Applicability: preserve the desktop Left/Right/Home/End contract, but do not automatically label the responsive rail as tabs unless its all-visible-card behavior is intentionally defined as a tab relationship.
- The MDN [CSS scroll snap guide](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll_snap) identifies horizontal overflow, child snap positions, and scroll padding/margins as the native building blocks for pannable rails. Applicability: reuse proximity snapping for approximately three markers, keep `overflow-x: auto` and touch panning, and add destination `scroll-margin` so focused cards remain visible below the fixed header.
- The web.dev [responsive images guidance](https://web.dev/learn/design/responsive-images) emphasizes serving images sized for their rendered use and retaining lazy loading for below-fold assets. Applicability: replacing 56px mosaic preview sources with bounded 160px WebPs addresses transfer and decode cost at the source; lazy loading alone is not an adequate substitute, and dialog sources remain lazy and full resolution by explicit scope.
- WCAG 2.2 [Focus Visible guidance](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible) requires keyboard users to perceive the focused component. Applicability: both responsive markers and mosaic buttons need non-color-only `:focus-visible` treatment, and programmatically focused evidence destinations need a visible but non-persistent focus style.
- WAI guidance for [On Focus](https://www.w3.org/WAI/WCAG22/Understanding/on-focus) warns against unexpected context changes merely from moving focus. Applicability: the choice between arrow-key focus-only navigation and automatic scroll-to-card behavior is a consequential interaction decision that should be confirmed rather than inferred.

## Decision Register

### Decision Points

#### Decision Point: Responsive rail construction and semantics

- Applies to: Task 2 responsive markup and Task 4 initialization; the cards remain simultaneously visible, so multiple valid control structures exist and produce different fallback, semantics, and maintenance outcomes.
- Tag: ask
- Rationale/Resolution: The input requires a responsive rail, Arrow-key navigation, and a functional stacked-card fallback but does not specify whether rail controls are static or generated, or whether they are navigation links, generic buttons, or tabs.
- Alternative: Static navigation links enhanced by JavaScript.
  - Description: Add a localized list/navigation region containing 13 native anchors mapped to card IDs, then enhance focus, edge, and scroll behavior in JavaScript.
  - Trade-offs: The rail remains useful without JavaScript and has native destinations, but it adds substantial duplicated markup to all six static documents.
  - Expected codebase impact: Six HTML rail copies, card IDs, responsive CSS, a dedicated JavaScript enhancer, and parity tests.
- Alternative: Runtime-generated button rail.
  - Description: Derive 13 marker buttons from the existing responsive cards when JavaScript initializes, leaving only the stacked cards in source markup.
  - Trade-offs: The card list remains the single source of marker data and route drift is reduced, but the rail does not exist without JavaScript and generated controls require careful accessible naming.
  - Expected codebase impact: Smaller HTML changes, more JavaScript DOM construction, enhancement-gated CSS, and browser tests for generation failure.
- Alternative: Static ARIA tablist mapped to cards.
  - Description: Add 13 static `role="tab"` controls referencing the 13 visible cards as tabpanels while leaving all panels displayed.
  - Trade-offs: It reuses the existing desktop roving-tab pattern, but the all-visible content model departs from the usual one-selected-panel tab contract and increases semantic/testing complexity.
  - Expected codebase impact: Six tablist copies, new ARIA relationships on cards, shared tab utilities or a second initializer, and assistive-technology validation.

#### Decision Point: Responsive marker activation model

- Applies to: Task 4 keyboard and focus behavior; Arrow keys can either navigate only within the rail or immediately move the page to evidence.
- Tag: ask
- Rationale/Resolution: The input requires Arrow-key navigation and says selecting a marker scrolls/focuses its card, but it does not define whether focus movement itself counts as selection.
- Alternative: Focus with arrows, activate with Enter/Space or click.
  - Description: Arrow keys move roving focus and center the marker; explicit activation scrolls and focuses the destination.
  - Trade-offs: It avoids repeated page jumps while exploring markers and aligns activation with native controls, but keyboard users need one additional keystroke.
  - Expected codebase impact: Separate focused and selected states, key handlers for arrows plus activation, and fixture assertions for both.
- Alternative: Automatic activation on Arrow focus.
  - Description: Every Arrow-key focus move immediately selects the marker, scrolls to the card, and focuses the destination.
  - Trade-offs: Navigation is one-step and parallels the desktop automatic tabs, but each Arrow press changes page context and can move the rail out of view.
  - Expected codebase impact: A single focus-driven activation path plus page-scroll/focus coordination and stronger browser tests.
- Alternative: Arrows select without moving card focus.
  - Description: Arrow keys update and center the marker and scroll the associated card into view while focus remains in the rail; click/Enter moves focus into the card.
  - Trade-offs: The rail stays keyboard-continuous while evidence is previewed, but selection and destination focus have two distinct outcomes that need clear state semantics.
  - Expected codebase impact: Dual activation modes, selected-state attributes, and tests for focus retention versus transfer.

#### Decision Point: Responsive card focus destination

- Applies to: Task 2 card attributes, Task 3 focus styling, and Task 4 activation; the 13 cards do not share one existing native focus target.
- Tag: ask
- Rationale/Resolution: The input explicitly permits focus to move “to that card or its primary focus target,” leaving a choice that changes focus order and what users encounter after navigation.
- Alternative: Focus the card container.
  - Description: Give every mapped `<li>` a stable ID and `tabindex="-1"` and focus the card itself after scrolling.

#### Decision Point: Responsive marker state synchronization

- Applies to: Task 3 marker styling and Task 4 state management; ordinary vertical card scrolling may or may not update the rail’s selected/current marker.
- Tag: ask
- Rationale/Resolution: The input requires selecting markers but does not define what happens to selection when the user scrolls the card list directly.

  - Description: Update current/selected state only after rail activation and leave it unchanged during ordinary page scrolling.
  - Trade-offs: State is simple and deterministic, but it may no longer correspond to the card currently in view after manual scrolling.

- Alternative: Synchronize to the visible card.

  - Trade-offs: It avoids stale state and observer complexity, but users lose a persistent visual indication of their last rail choice.
  - Expected codebase impact: Minimal state logic and reduced CSS/ARIA assertions.
