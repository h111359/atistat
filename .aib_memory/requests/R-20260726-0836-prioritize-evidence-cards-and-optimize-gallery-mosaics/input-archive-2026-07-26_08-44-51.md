### Goal

Improve the Experience section so evidence cards receive primary visual emphasis, timeline navigation remains available across desktop and mobile layouts, and gallery mosaics load efficiently while clearly communicating that they are interactive.

### Users and Need

- Primary users are Bulgarian- and English-speaking visitors evaluating ATISTAT’s professional experience and project evidence.
- Visitors currently encounter an oversized desktop timeline before the selected evidence card.
- Portrait and other layouts at 860px or below currently hide the timeline rail entirely and show only stacked cards.
- Gallery mosaics use full-resolution source images for very small previews, increasing transferred data.
- Gallery mosaics resemble decorative imagery and do not provide a sufficiently visible click affordance.
- Site maintainers need all duplicated localized documents and shared assets to remain synchronized.

### Business Value

- Give project evidence greater visual priority.
- Make chronological navigation available on every supported responsive layout.
- Reduce normal-page gallery preview payload.
- Improve gallery discoverability for pointer, touch, keyboard, and assistive-technology users.
- Priority ranking is not applicable because this is a direct implementation request already selected for the current workflow.

### Scope

- Update all six Experience timeline documents:
  - `index.html`
  - `index-bg.html`
  - `index-en.html`
  - `index.html?lang=bg.html`
  - `index.html?lang=en.html`
  - `opit/index.html`
- Retain `opit/index.html`; it is an end-user route referenced by English project pages, `index.html?p=6.html`, the sitemap, and automated route tests.
- Update both byte-identical shared stylesheet files.
- Update both byte-identical shared JavaScript files where mobile-rail interaction requires it.
- Generate optimized local thumbnail assets for the gallery mosaics.
- Update the static checks and browser interaction fixture.
- Update `.aib_memory/context.md` to describe the resulting current architecture and remaining full-gallery payload risk.

### Desktop Experience Requirements

- Apply the desktop presentation above 860px.
- Present elements in this order:
  1. Selected evidence card.
  2. Localized “Select a stage” instruction.
  3. Compact desktop timeline.
- Preserve the evidence card’s current dimensions, typography, content, and visual treatment.
- Preserve approximately five complete milestones in the visible timeline viewport.
- Preserve milestone order, selection behavior, active-item centering, free horizontal panning, snap alignment, edge fades, Previous/Next controls, keyboard operation, tab semantics, and accessible state attributes.
- Reduce desktop milestone image heights by approximately 35–40% from their current values.
- Reduce the two endpoint main-year labels to approximately 16–20px.
- Reduce the two endpoint captions to approximately 9–10px.
- Establish card emphasis through placement and reduced timeline prominence rather than enlarging or restyling the card.

### Responsive and Mobile Experience Requirements

- Apply the responsive presentation at every viewport width of 860px or less.
- Preserve all thirteen existing stacked evidence cards and their current content order.
- Present the responsive section in this order:
  1. Experience heading and introduction.
  2. New horizontally scrollable milestone rail.
  3. Existing stacked evidence cards.
- Show all thirteen milestones in the new rail.
- Each marker must display a compact project or company image and its year, reusing the corresponding card image source.
- Approximately three complete markers must be visible at once.
- Do not include the desktop `2000` and `2026` endpoint blocks.
- Do not include separate Previous/Next buttons.
- Support touch and trackpad panning, visible edge fades, and keyboard-arrow navigation.
- Selecting a marker must scroll to its corresponding stacked card and move keyboard focus to that card or its primary focus target.
- Use immediate scrolling instead of animation when reduced motion is requested.
- Preserve a functional stacked-card fallback if JavaScript is unavailable.

### Gallery Mosaic Performance Requirements

- Create one optimized thumbnail for each of the 28 unique images used by the seven four-image mosaic previews.
- Each thumbnail must:
  - Use WebP format.
  - Be 160×160 pixels.
  - Be no larger than 20KB.
  - Preserve a suitable center crop for the existing square preview treatment.
- Use these thumbnails in every desktop and mobile mosaic across all six documents.
- The same thumbnail URL must be reused where a project mosaic is duplicated between desktop and mobile markup.
- Full-resolution PNG and JPEG gallery sources must no longer be referenced by mosaic preview images.
- Preserve the existing full-resolution sources inside the native gallery dialog.
- Preserve lazy loading and asynchronous decoding where applicable.

### Gallery Mosaic Affordance Requirements

- Add a persistent translucent overlay to every mosaic.
- Include a recognizable local or inline gallery icon.
- Use the visible localized text:
  - Bulgarian: `Виж галерия`
  - English: `View gallery`
- Provide clear hover and keyboard-focus feedback.
- Keep the complete mosaic as one native button and preserve its existing accessible name.
- Ensure the overlay does not intercept pointer input.
- Preserve native dialog opening, project filtering, close behavior, keyboard accessibility, and invoker-focus restoration.

### Localization and Parity Requirements

- Apply Bulgarian labels to the three Bulgarian documents.
- Apply English labels to the three English documents, including `opit/index.html`.
- Preserve correct relative asset paths in `opit/index.html`.
- Keep both shared CSS copies byte-identical.
- Keep both shared JavaScript copies byte-identical.
- Preserve the same thirteen-milestone dataset and interaction contract across all six documents.

### Constraints

- Preserve the static-site architecture.
- Do not introduce third-party JavaScript, a package dependency, or a build pipeline.
- Store all new thumbnails locally.
- Preserve visible and operable content without JavaScript wherever practical.
- Continue honoring reduced-motion preferences.
- Prevent horizontal page overflow at the existing minimum supported width of 320px.
- Do not modify project names, dates, descriptions, company attribution, gallery membership, or source-image order.

### Out of Scope

- Optimizing or replacing the full-resolution images displayed inside the opened gallery.
- Removing the original PNG and JPEG gallery files.
- Redesigning or enlarging evidence cards.
- Removing or filtering stacked mobile cards.
- Changing project-detail page content.
- Changing gallery-dialog functionality beyond preserving current behavior.
- Changing the thirteen timeline milestones or their chronology.

### Assumptions

- The existing 860px breakpoint remains the boundary between desktop panels and responsive stacked cards.
- The current timeline and gallery data are authoritative.
- Reusing responsive-card image URLs in the mobile rail does not create duplicate network transfers because the browser cache can reuse the same asset.
- Thumbnail optimization addresses normal Experience-section loading; full-dialog payload remains a separate known concern.

### Success Criteria

- All six documents render the selected desktop evidence card above the instruction and compact timeline at widths above 860px.
- Desktop evidence cards retain their current dimensions, typography, and content.
- Desktop milestone images are approximately 35–40% shorter while about five complete milestones remain visible.
- Endpoint main years render within approximately 16–20px and endpoint captions within approximately 9–10px.
- At widths of 860px or less, a thirteen-marker rail appears above the unchanged stacked-card list.
- Approximately three complete mobile markers are visible at once.
- Touch panning, keyboard-arrow navigation, edge fades, card scrolling, and focus movement work on the mobile rail.
- Reduced-motion mode performs immediate card navigation without animated scrolling.
- Every mosaic uses 160×160 WebP thumbnails no larger than 20KB.
- No mosaic references a full-resolution PNG or JPEG gallery source.
- Full-resolution images remain available in the native dialog.
- Every mosaic visibly displays the correct localized overlay text and gallery icon.
- Existing dialog accessibility and focus restoration continue working.
- No horizontal page overflow occurs at 320px.
- Both shared CSS copies and both shared JavaScript copies remain byte-identical.
- Updated static tests and browser smoke checks pass without first-party console errors.
