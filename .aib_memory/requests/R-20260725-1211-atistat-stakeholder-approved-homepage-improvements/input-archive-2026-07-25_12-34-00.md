### Additional modifications to the above instructions

After additional analysys were found issues in the above instructions. The following corrections MUST be applied:

#### H-01 — The gallery performance plan contradicts the performance goal

The prompt explicitly prohibits conversion and optimization and requires byte-identical deployment of all source images. The selected-project folder is 52.51 MiB. Lazy loading helps before the dialog opens, but it does not make a gallery of 32 large files lightweight; opening and scrolling the dialog can still transfer most or all of the payload.

The requirement also creates 160 image references across five HTML documents, although the browser will reuse the same 32 files per route.

**Impact:** slow modal rendering, high mobile data use, memory pressure, and likely poor experience on the field/slow-network scenario highlighted by the UX source.

**Required correction:**

- preserve originals in `workdir`, but generate web-ready derivatives in uploads;
- use WebP or optimized JPEG/PNG, responsive `srcset`/`sizes`, explicit dimensions, and thumbnails;
- load full-resolution media only on deliberate enlargement;
- set measurable per-image and total-gallery budgets;
- keep the corrected count of 32.

#### H-02 — Supplied project facts are intentionally discarded, and two names drift from the workbook

At line 213, the prompt says not to display the workbook’s building type, activity, status, year, or experience fields. Those fields occupy rows 74–122 and are the only stakeholder-supplied factual context for the seven new projects.

“Gallery-only” resolves presentation and the absence of dedicated project links; it does not necessarily mean “photos and heading only.” A compact facts block inside each gallery group can remain gallery-only.

The prompt also uses:

- `Луй Айер`, while workbook row 103 says `ап. Луи Айер`;
- `Аркадия`, while workbook row 110 says `ап. Аркадия`.

The source folder itself contains mixed `Луй`/`Луи` spellings, so the workbook should govern the public label.

**Impact:** loss of approved content, weaker portfolio evidence, and visible naming errors.

**Required correction:**

- clarify whether “gallery-only” forbids only routes/case studies or also compact factual captions;
- preferably render the stakeholder-provided type, activity, status, year, and experience under each project heading;
- use `ап. Луи Айер` and `ап. Аркадия` unless the stakeholder explicitly chooses shorter marketing labels.

### H-03 — A public, sitemap-listed homepage duplicate is omitted

The prompt hard-limits the affected documents to five root files. However, `opit/index.html` is a 518-line English page that reproduces the homepage structure, and `wp-sitemap-posts-page-1.xml` exposes `/atistat/opit/`.

Leaving it unchanged means a discoverable route will retain the old eight-entry timeline, no CTA, no selected-project gallery, no partners, old language behavior, and no new SEO metadata.

**Impact:** inconsistent public experience and failed “full English parity.”

**Required correction:** either include `opit/index.html` in the implementation and acceptance matrix or explicitly redirect/remove/noindex that route and update the sitemap. Do not silently ignore it.


### H-04 — Full parity lacks the required shared CSS/markup migration

Only `index.html` currently contains:

- `.at-hero__sub` markup and styles;
- `.at-hero__ctas` markup and styles;
- `section#why` and its styles;

The other four root variants and `opit/index.html` lack these elements. Their only theme styling comes from `main.css`.

The prompt says to “replace” hero text in all files even where the element does not exist, and to copy Why/FAQ while leaving their CSS in the primary document’s inline block. It adds shared CSS for new CTA/partners/gallery/service features, but not for the existing parity sections.

**Impact:** an implementer can satisfy the text requirement incompletely or create unstyled parity sections.

**Required correction:**

- explicitly add missing hero sub-text and hero CTA markup to the applicable copies;
- move `.at-hero__sub`, `.at-hero__ctas`, `.at-why*`, and `.at-faq*` rules into `main.css`;
- remove duplicate inline copies from `index.html`;
- specify the exact FAQ/Why markup and styling destinations.

### H-05 — SEO handling risks duplicate and incorrect canonical URLs

The prompt adds descriptions and social metadata but omits:

- `<link rel="canonical">`;
- `hreflang="bg"`, `hreflang="en"`, and optionally `x-default`;

**Impact:** duplicate-content indexing, split ranking signals, incorrect social previews, and only partial fulfillment of workbook row 31’s local-SEO intent.

**Required correction:**

- give all BG snapshots the BG canonical and all EN snapshots the EN canonical;
- add reciprocal hreflang links;
- align `og:url` with the canonical rather than the local snapshot filename;
- verify whether the EN canonical is `/index-en.html`, `/?lang=en`, or another production route;
