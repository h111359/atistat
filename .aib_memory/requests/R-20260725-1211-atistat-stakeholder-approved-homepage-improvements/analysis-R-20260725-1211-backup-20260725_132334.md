**Request ID:** R-20260725-1211

### Background

The ATISTAT website is a static bilingual marketing site for a Bulgarian construction and investment company. The primary Bulgarian homepage (`index.html`) and four companion documents (`index-bg.html`, `index.html?lang=bg.html`, `index-en.html`, `index.html?lang=en.html`) currently diverge in content and lack several features approved by the company's stakeholder via a stakeholder workbook (`ATISTAT_idei_za_podobrenie_Versia_5 , 24.07.2026 - HH.xlsx`). The stakeholder reviewed a proposal set and made explicit decisions about what to add, remove, modify, and defer.

A prior assessment (`workdir/improvements-20260725_0736-assessment.md`) reviewed an earlier version of this implementation prompt and found it suitable, noting that the strong areas are the exact hero/caption changes, removals, nine-entry timeline spec, five route families, 32-image count, and clear exclusions. This request is the current, authoritative implementation prompt derived from those decisions.

### Industry Knowledge and Best Practices

**1. Native `<dialog>` element (HTML Living Standard + WHATWG):**
The native `<dialog>` element with `showModal()` is fully supported in all current browsers (Chrome 37+, Firefox 98+, Safari 15.4+). Using `showModal()` automatically creates a top-layer modal context, traps focus within the dialog, enables native `Escape` key closing, and sets the `::backdrop` pseudo-element. This eliminates the need for custom focus-trap logic. Applicability: directly prescribed by the input; best practice for accessible modal implementation without third-party dependencies.

**2. WCAG 2.1 AA requirements (W3C):**
- Success criterion 2.5.5 (Target Size, Level AAA) recommends 44×44 CSS pixels; WCAG 2.1 AA requires 24×24 (SC 2.5.8 in 2.2). The prompt requires 44×44 for language controls. Padding-only approaches preserve the visual text size while expanding the interactive area. Using `display: inline-flex; min-width: 44px; min-height: 44px; align-items: center; justify-content: center` achieves this cleanly.
- Non-color-only active state (SC 1.4.1): A visible weight or border treatment combined with color satisfies this. A background chip or underline-only approach risks failing if the underline is too thin. A `border-radius` background chip on `.at-lang__opt.is-active` is a reliable pattern used by major design systems (Material, Fluent).
- `aria-current="page"` on the active navigation item is prescribed by ARIA 1.2 and widely supported. Applicability: directly required by the prompt.

**3. Responsive grid for gallery (CSS Grid / MDN, Smashing Magazine):**
`grid-template-columns: repeat(auto-fill, minmax(200px, 1fr))` creates an intrinsically responsive grid without media-query breakpoints. Combined with `gap` and `max-height` on the dialog, this is the most maintainable approach. For the gallery dialog, a fixed-column approach per breakpoint (3/2/1 col) is more predictable for large portrait images. Industry practice for photo galleries leans toward fixed columns to avoid the "orphan image" problem in auto-fill grids. Applicability: the input prescribes responsive grid; the exact implementation is a decision point.

### AI Agent Critique

- **Scope mismatch: `--active-progress` CSS variable on timeline.** `index.html` hardcodes `--active-progress: 42.857142857143%` (= position 3 of 7 in the old 8-entry layout where Montekanal was active at index 3 of indices 0–7). After inserting ATISTAT at index 6, the total becomes 9 entries. The active entry (index 3 / Montekanal, 4th of 9) should produce `--active-progress: 33.333%` (= 3/8 progress through the bar). This computed value must be updated in all 5 documents; the implementation agent must derive it from the layout.
- **Scope mismatch: `at-hero__art` lazy vs. eager loading.** The input says "Preserve `loading="eager"` and `fetchpriority="high"` for the primary `index.html` hero image." `index.html` currently sets the hero Elemag image to `loading="eager" decoding="async" fetchpriority="high"`. `index-bg.html` and `index.html?lang=bg.html` use `loading="lazy"` for the same hero image. The prompt does not explicitly call out fixing the lazy loading on the BG variants — only preserving the primary one. This divergence should be noted but not corrected beyond what the prompt specifies.
- **Inconsistency: WhatsApp `target`/`rel` on EN homepage.** `index-en.html` contacts section needs WhatsApp entry added if absent. The WhatsApp entry in index.html has `target="_blank" rel="noopener noreferrer"` — this is the correct pattern per the prompt spec.
- **Risk: `aria-label` on BG homepage `<a class="at-lang__opt is-active" href="">BG</a>`.** The href is empty string, which triggers same-page reload. The prompt requires only `aria-current="page"` — it does not require changing the href. This is not a change but should be documented.
- **Risk: `opit/index.html` out of scope.** The `opit/` directory contains an English experience route. The prompt explicitly limits scope to the five root homepage documents. `opit/index.html` must not be modified even though it shares the same timeline structure.
- **Inconsistency: `index.html` inline CSS removal vs. inline CSS belonging to scope.** `index.html` has a document-local `<style>` block containing CSS for `.at-stats`, `.at-testimonials`, `.at-social-links`, `.at-whatsapp-fab`, `.at-hero__sub`, `.at-hero__ctas`, `.at-why`, `.at-faq`, `.at-social-link`. After removing stats, testimonials, and social block, the corresponding CSS selectors become orphaned. The prompt explicitly requires removing those selectors. However, the CSS block also contains the Why and FAQ styles and the hero sub-text styles. These must be retained. The implementation agent must surgically remove only the stat, testimonial, and social-link selectors.
- **Inconsistency: FAQ `<details>/<summary>` pattern vs. aria-expanded requirement.** The current FAQ uses `<details>/<summary>`. Native `<summary>` does not expose `aria-expanded` — only `open` attribute state. Automated accessibility checkers like axe-core will not flag this, but the input's acceptance criterion #26 mentions "required ARIA states." The exact FAQ interaction pattern is a decision point.
- **Risk: image payload size.** The 32 gallery images total approximately 52.5 MiB (per prior assessment). All are marked `loading="lazy"` per the prompt. This mitigates initial load impact, but users on slower connections who open the modal will download large files. The prompt prohibits image optimization, so this is an accepted trade-off.
- **Missing: `<script type="speculationrules">` in `index-bg.html` and other shorter documents.** `index.html` contains a prefetch speculationrules block that excludes media and query routes. The shorter documents also carry this block. This is existing content and should not be affected by the implementation.
- **Risk: dialog `id="selected-projects-dialog"` uniqueness.** Each file is a separate HTML document, so the same ID appears in each file — this is correct. No ID collision within a document.
- **Risk: timeline `aria-controls` associations.** After inserting the ATISTAT entry at index 6, all subsequent tab buttons and panels must be renumbered (`aria-controls="timeline-panel-6"` for ATISTAT, `timeline-panel-7` for OBB, `timeline-panel-8` for BSS). The corresponding `<article id="timeline-panel-6/7/8">` must be added/renumbered. The `is-active` state on OBB (currently index 6 `timeline-panel-6`) must not be carried forward — the Montekanal active state should be preserved at index 3.
- **Inconsistency: duplicate SVG IDs in header.** Context.md issue: "Header and footer inline logos repeat the same eight HTML identifiers within the primary homepage." This is pre-existing and out of scope for this request.
- **Missing: navigation anchor for CTA.** The current nav (`section#contacts` link in header) does not include an anchor for the new CTA section or the new Partners section. The input does not require updating the navigation links. Acceptable.
- **Risk: `index.html?lang=bg.html` and `index.html?lang=en.html` file naming.** These files have query-string-like names (`index.html?lang=bg.html`). They are valid static files on the filesystem but not conventional. The implementation must treat them exactly as named without renaming.

### Edge Cases

- **Thirty-third image scenario:** The prompt explicitly addresses this: "If the source directory contains a genuinely new thirty-third image at implementation time, include it in the matching project group." At analysis time, exactly 32 images exist. No thirty-third image is present.
- **Empty CTA section on very narrow mobile (320px):** The CTA four-button row must wrap or stack. CSS flex-wrap with a min width per button is the standard approach. The dial between wrapping cleanly and overcrowding at 320px requires careful min-width choice.
- **Viber URI on desktop browsers without Viber installed:** The `viber://` scheme will produce no action on desktop Chrome/Firefox/Safari without Viber installed. The prompt handles this by requiring descriptive `title` and `aria-label`. The implementation must not add `target="_blank"` to Viber links (the prompt explicitly specifies this).
- **ATISTAT timeline entry "no added claim" description:** The nine-entry table lists no description for ATISTAT (year 2024, position 7). The timeline panel must not contain a `<p class="at-tlpanel__desc">` element for ATISTAT — or it must be empty. This edge case should be confirmed.
- **Active timeline entry after ATISTAT insertion:** The current active entry (Montekanal, index 3 of 8) remains active at index 3 of 9. The `--active-progress` variable must be recalculated.
- **`index.html` `<style>` block after removals:** The style block will have orphaned selectors for `.at-stats`, `.at-testimonials`, `.at-social-links`, and `.at-whatsapp-fab`. The prompt requires removing exactly these selectors. Care must be taken not to remove the Why and FAQ styles that are in the same block.
- **`index.html` unique hero loading attributes:** Only `index.html` carries `loading="eager" decoding="async" fetchpriority="high"` on the hero Elemag image. The other BG documents already use `loading="lazy"`. The implementation must not add `loading="eager"` to the BG companions.
- **Partners section before `section#why` which may be absent:** For the four shorter documents that currently lack `section#why`, the Partners section must still be inserted after `.at-contact-cta`. In those documents the insertion point is simply after CTA and before whatever section follows (e.g., contacts).
- **`index-bg.html` vs `index.html?lang=bg.html` byte-equality:** The prompt does not require these two files to be byte-identical, only content-equivalent. This distinction matters because the two files may have different `og:url` values and language switcher `href` values.
- **Timeline mobile card for ATISTAT:** The mobile card uses `at-tlcard--logo` and should navigate to `/` via `data-href="/"`. The existing mobile card pattern for logo entries uses `data-href` + `style="cursor:pointer"`. This must be replicated for the ATISTAT card.
- **Versioned CSS/JS byte-identical pair:** The prompt requires keeping `main.css?ver=1784544801.css` byte-identical to `main.css` and `main.js?ver=1784544801` byte-identical to `main.js`. Every change to the canonical files must be mirrored to the versioned copies. The simplest approach is to copy the canonical file to the versioned name after each edit session.

### Decision Points

#### Decision Point: FAQ keyboard interaction pattern
- Tag: ask
- Rationale: The current FAQ uses native `<details>/<summary>`. Native `<summary>` is keyboard-operable (Enter/Space toggles, browsers expose it to AT as a disclosure widget). However, it does not expose an explicit `aria-expanded` attribute — screen readers receive the open/closed state via the `open` attribute of `<details>`, not `aria-expanded`. The acceptance criterion "FAQ controls must retain or gain keyboard-operable buttons and correct expanded/collapsed ARIA state" is ambiguous: native `<details>` does expose expanded state to AT (via role=group and the `open` attribute), but the wording "correct expanded/collapsed ARIA state" could be interpreted as requiring `aria-expanded` on a `<button>` element. The two alternatives produce significantly different implementation scope:
  - Alternative A: Retain `<details>/<summary>` — keyboard-operable, native browser disclosure semantics, no `aria-expanded` attribute, WCAG 2.1 AA compliant.
  - Alternative B: Convert to `<button>` + `<div>` controlled disclosure — adds `aria-expanded` attribute, requires JS for toggle, more explicit ARIA pattern, more implementation work.
  > Pending user decision: both alternatives are accessible; the choice affects implementation scope.
