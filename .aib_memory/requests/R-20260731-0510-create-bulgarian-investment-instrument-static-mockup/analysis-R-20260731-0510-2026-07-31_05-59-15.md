## Overview

- Request ID: R-20260731-0510
- Request title: Create Bulgarian investment instrument static mockup

### Background

ATISTAT needs a vivid, portable demonstration of the residential-investment analysis product described in `workdir/investment_instrument_input.md`, so stakeholders can explore the intended workflows before funding or building the production cloud application.

### Scope

The request covers a Bulgarian-language, dependency-free static website under `workdir/investment_instrument/`; a landing page; representative analyst, review, source-governance, and reporting interactions; locally stored JSON data; an accessible full HTML representation of the source requirements; a help page; a future-improvements page; and automated checks that the unpacked folder remains self-contained and usable.

### Out of scope

The iteration does not build the production cloud system, connect to live listing feeds, provide authentication or durable multi-user workflows, automate legal or financial actions, make investment recommendations without human review, modify the public ATISTAT website, or update `.aib_memory/context.md`.

## Input Interpretation

### User Original Inputs

The developer requested creation of `workdir/investment_instrument/` containing a Bulgarian static website whose `index.html` is a complete mockup of `workdir/investment_instrument_input.md`. The landing page must visibly link to a separate, convenient, complete HTML rendering of the requirements. The package must also include locally stored JSON data based on accessible real external data where possible and visibly fabricated data otherwise, a help page, and a future-improvements page with simple examples and selectable evolution options. The folder must be suitable for ZIP distribution, run without installation or external runtime dependencies, demonstrate the idea as vividly and completely as practical without pretending to be production-ready, and mimic feasible functionality. Because the work is experimental, the developer explicitly instructed that `context.md` must not be changed yet.

### AI interpretation

The deliverable is a self-contained, Bulgarian-language product prototype rather than a marketing landing page or production application. It should present the source specification through a coherent multi-page application shell and a representative end-to-end analyst journey: select a profile, explore and filter synthetic Sofia apartment offers, inspect source quality, compare offers, adjust assumptions, review the two investment strategies and two financing modes, examine cash flows, risk, confidence, sensitivity, due-diligence checks, and a human-review recommendation, then exercise illustrative export and approval actions. Administrative, notification, audit, help, roadmap, and source-governance concepts should be visible at mockup depth.

Official data must be snapshotted with source URL, publisher, observation date, retrieval date, unit, scope, and a real/synthetic classification. Official aggregate indicators may inform the market and financing context, but they must not be presented as property-level evidence. Listing records, repairs, rents, risks, recommendations, and user activity should be synthetic and explicitly labeled. The website must continue to work from its own folder after extraction; no CDN, remote font, remote image, build step, package installation, backend, or secret may be required.

### Edge Cases

- Opening the package through `file://` may block local JSON fetches, while an HTTP-served copy may work; the selected launch contract must be tested explicitly.
- JavaScript may be disabled or fail; navigation, requirements, help, future ideas, source notes, and core offer summaries should remain readable.
- A JSON snapshot may be missing, malformed, empty, stale, preliminary, or use a changed base year; the UI must show an intelligible data-status state rather than fabricated precision.
- Synthetic and real values may appear in the same view; each must carry an unambiguous origin/type label that is not color-only.
- Financial models may encounter zero interest, zero equity, negative cash flows, no IRR, multiple IRRs, invalid horizons, missing rent, or break-even values outside the tested range.
- Comparison may have fewer than two offers, more than the supported maximum, incompatible currencies or periods, or offers excluded by hard constraints.
- A critical due-diligence warning must override a favorable numeric score without being mistaken for a legal conclusion.
- Changing assumptions must not silently mutate a “locked” sample analysis; the mockup should either create a visible draft state or clearly label the interaction as ephemeral.
- Browser storage may be unavailable, full, or contain stale data from an older prototype version; a visible reset path and safe defaults are required if persistence is selected.
- JSON/CSV download and print-to-PDF behavior differs across browsers and `file://` contexts; fallbacks must be visible.
- Bulgarian labels, currency values, long table headings, formulas, and the complete 1,322-line requirements document must reflow on small screens without horizontal page failure.
- Keyboard focus must return after dialogs close, tab order must remain logical after filtering, and status must not be conveyed by color alone.
- The future-improvements selector must not imply that a choice is saved centrally or approved when it exists only in the local browser.
- ZIP extraction may preserve a nested top-level folder; all paths must be relative and case-correct.
- The source requirements or official snapshots may change after implementation; the package must show the snapshot date and should not claim live freshness.
- The public ATISTAT site and `.aib_memory/context.md` must remain untouched even if brand assets or production concepts are referenced.

## Proposed Solution

### High-Level Concept

Build an isolated, multi-page Bulgarian static prototype that uses a shared accessible application shell, locally snapshotted official indicators, clearly synthetic offer data, and selected client-side interactions to demonstrate the production concept without claiming production capabilities.

## Decision Register

### Decision Points

#### Decision Point: Landing Experience

- Tag: ask
- Applies to: Task 1 `index.html`; the landing page can prioritize daily analyst work, stakeholder orientation, or a guided narrative, producing substantially different hierarchy and interaction.
- Alternative Analyst Dashboard: Open directly on ranked offers, alerts, market context, tasks, and shortcuts. Trade-offs: strongest product realism and quickest interaction, but less introductory explanation; impact: dashboard-heavy `index.html` and supporting data widgets.
- Alternative Product Overview: Lead with the problem, value, modules, and calls to enter the mock workflow. Trade-offs: clearest for first-time stakeholders, but less application-like; impact: presentation-led `index.html` with workflow pages one click deeper.
- Alternative Guided Demonstration: Lead with a numbered end-to-end walkthrough. Trade-offs: controls the story and supports presentations, but constrains free exploration; impact: stepper state and tour content in `index.html` and `app.js`.
- Rationale/Resolution: The request calls `index.html` both a landing page and a complete mockup but does not establish which experience owns the first screen.

#### Decision Point: Role Coverage

- Tag: ask
- Applies to: Tasks 1 and 3; the source specification defines Administrator, Analyst, and Observer/Approver, but the mockup depth for each role is unspecified.
- Alternative Analyst First with Role Switcher: Fully demonstrate analyst flows and provide lighter administrator/reviewer states. Trade-offs: broad coverage with manageable depth, but secondary roles are less complete; impact: shared role switcher and conditional panels.
- Alternative Analyst Only: Model only the main analyst journey. Trade-offs: deepest core experience and smallest scope, but weak coverage of governance and approval; impact: fewer states and a smaller `administration.html`.
- Alternative Three Separate Role Views: Give each role a distinct dashboard and workflow. Trade-offs: strongest role clarity, but highest page/state volume and duplicated content; impact: additional role-specific sections or pages and tests.
- Rationale/Resolution: “Complete mockup” does not resolve how production roles should be represented in an experimental package.

#### Decision Point: Visual Identity

- Tag: ask
- Applies to: Task 1 `styles.css`; the mockup can inherit ATISTAT branding, introduce a product identity, or remain a neutral wireframe.
- Alternative ATISTAT Corporate: Reuse the green, ink, cream, local typography, and approved local logo treatment. Trade-offs: strong continuity and stakeholder familiarity, but may blur the boundary with the public website; impact: local brand assets and ATISTAT-derived design tokens.
- Alternative Standalone Product: Create a distinct data-product visual system while retaining a small ATISTAT endorsement. Trade-offs: clearly separates the internal tool, but requires new visual decisions; impact: new local tokens, iconography, and product mark.
- Alternative Neutral Prototype: Use an intentionally unbranded professional dashboard. Trade-offs: keeps discussion focused on function, but is less vivid and less client-ready; impact: generic tokens and no brand assets.
- Rationale/Resolution: Neither the request nor the product specification sets a visual identity for the standalone application.

#### Decision Point: Offline Launch Mode

- Tag: ask
- Applies to: Tasks 1, 2, and 5; local JSON access and browser behavior differ between direct file opening and HTTP serving.
- Alternative Dual Mode: Support direct `index.html` opening through a local data bootstrap and also work under a standard static server. Trade-offs: most portable, but duplicates canonical JSON into a runtime bundle that must be parity-tested; impact: `demo-data.js`, JSON parity checks, and two smoke modes.
- Alternative Direct File Only: Optimize entirely for double-click use. Trade-offs: simplest for recipients, but constrains fetch, routing, and some browser APIs; impact: all data loaded through scripts/inline payloads and purely relative multi-page navigation.
- Alternative Static Server Only: Require a documented standard local server command. Trade-offs: clean JSON fetch semantics, but “unzip and run” now depends on a preinstalled runtime and command-line use; impact: no mirrored data bundle and server-specific instructions/tests.
- Rationale/Resolution: The request prohibits installation and requires portability but does not explicitly define the launch action recipients will use.

#### Decision Point: Demo State Persistence

- Tag: ask
- Applies to: Tasks 1, 3, and 4; filters, shortlist, review choices, assumptions, and roadmap selections can reset or persist locally.
- Alternative Local Persistence with Reset: Save non-sensitive demo state in browser storage and provide a visible reset. Trade-offs: supports a convincing continued journey, but can leave stale state and needs versioned defaults; impact: storage adapter, migration/reset logic, and tests.
- Alternative Session Memory Only: Preserve state while pages are open but reset on a new session. Trade-offs: predictable demos with less residue, but multi-page navigation may require URL/session techniques; impact: session storage or serialized navigation state.
- Alternative Stateless Pages: Reset every page to canonical sample values. Trade-offs: most deterministic and robust, but interactions feel less connected; impact: no storage layer and simpler fixtures.
- Rationale/Resolution: The request asks to mimic feasible functionality but does not state whether recipient choices should survive navigation or reload.

#### Decision Point: Financial Model Depth

- Tag: ask
- Applies to: Task 3 `analysis.html` and `calculations.js`; the source specification contains substantially more calculations than a static demonstration can faithfully implement.
- Alternative Hybrid Core Calculator: Recalculate acquisition, loan, repair, flip/rent cash flow, ROI, NPV, and selected sensitivity live while using labeled sample outputs for advanced metrics. Trade-offs: credible interactivity with bounded risk, but not every displayed metric is live; impact: focused calculation engine plus explicit sample labels.
- Alternative Broad Formula Prototype: Implement all major cash-flow metrics, scenarios, risk components, and break-even calculations live. Trade-offs: most complete functional mimic, but materially larger validation burden and greater risk of appearing production-ready; impact: larger engine and fixture suite.
- Alternative Precomputed Scenarios: Let users switch among curated input/output snapshots without live formulas. Trade-offs: easiest to validate and present, but weakest demonstration of responsive analysis; impact: data-driven panels with minimal calculation code.
- Rationale/Resolution: “If some functionality can be mimic[ed] … it should be realized” does not define the acceptable boundary between live calculation and illustrative output.

#### Decision Point: Currency Presentation

- Applies to: Tasks 2 and 3; financial inputs, exports, and labels require a consistent base currency and any secondary display policy.
